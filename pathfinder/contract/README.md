# Contract corpus

Provisional test cases for Grid and Pathfinder Specification v0.4, section 12.
Each file in `cases/` is one request and its expected answer. The runner
(`test/test_contract.cpp`) sends every case through `handle()`. The HTTP suite
(`test/test_http.py`) also runs a representative path, reach and validation case
through the server. The same files are intended for the Java reference.

## Case file format

```json
{
  "name": "C-02-zigzag-example",
  "description": "What this case shows.",
  "endpoint": "/v1/path",
  "method": "POST",
  "headers": {"Content-Type": "application/json"},
  "config": {"token": "s3cret"},
  "request": { ... },
  "expect": {"status": 200, "body": { ... }}
}
```

- `method`, `headers` and `config` are optional. The defaults are `POST`, a JSON content type and no token.
- `request` is sent as JSON text. If it is a string, that string is sent as it is, so a case can hold broken JSON.
- `request_generator` (`{"repeat": " ", "times": 1048577}`) builds a very large body instead of storing it.
- For status 200 the whole body must be equal (key order does not matter).
- For an error, only `code` and (if present) `pointer` are compared. Wording in `title` and `detail` is free.

## Coverage

| Cases | What they check |
|---|---|
| C-01 to C-10 | Basic paths: straight line, start = goal, blocked or no-stop goal, detours, unreachable goal, exact budget, corner rules |
| C-11 to C-13 | The three diagonal metrics (true_diagonal, alternating with both parities) and cell cost multipliers |
| C-14 | Tie-breaking: many equal-cost paths must give exactly one answer |
| C-15, C-16 | `/v1/reach`, and a blocked start cell |
| C-17 | Size limits: 1x1 and 200x200 grids |
| C-18 | Every error in the spec's error table |

C-19 (expansion cap), C-20 (busy server) and C-21 (deadline) need the server limits and are added with them.

## Where the expected answers come from

**Not from the C++ code.** They were produced by a separate Python program written straight from the spec
(`tools/reference.py` in the author's notes, not part of this repo), then compared with the C++ code. They match.

Spec section 12 says the cases should be generated by the Java reference and reviewed by a person.
The fixtures remain provisional until Java generates the expected results and a reviewer checks them
against section 6. The Java comparison and the hand-marked obstacle-detection set are still required
for the Grid and Pathfinder Specification to advance from draft v0.4.

## Open questions the spec does not answer

These cases record the current behaviour, so a change should be a conscious one:

- `expansions` for GOAL_BLOCKED and GOAL_NO_STOP is 0 (no search runs).
- When start equals goal, `expansions` is 1.
- `expansions` is also present when `found` is false.
- The extra fields in the case-file format above (`request_generator`, `config`) are our addition.
